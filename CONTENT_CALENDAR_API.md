# Content Calendar: API reference

**Status: implemented** in `backend/src/content-calendar/`. Deploy steps: pull, `cd backend && npm install && npx prisma generate && npx prisma migrate deploy` (migration `20261031000000_content_calendar`, which only creates two new tables), then rebuild and restart the backend and frontend. No new environment variables.

Extra rule beyond the table below: changing a calendar to a shorter month is refused with a `409` if it has plans on days that month does not have (for example the 31st).

The frontend page is `/content-calendar` (sidebar: Workspace > Content Calendar). It talks to the backend through a proxy, so every request below is `GET/POST/... /api/content-calendar/...` in the browser and reaches the backend as `/content-calendar/...` with the user's `Authorization: Bearer` token. The page shows a friendly "not available yet" message until `/content-calendar/me` and `/content-calendar/calendars` respond.

## Who can do what

- **View:** every logged-in user.
- **Edit:** only users a super admin has ticked (stored per user, default off). Creating, changing and deleting calendars, posts and special days all need it. Reject others with `403`.
- **Manage access:** `super_admin` only (this is who can tick people).

## Data

One row per client and month. `days` is JSON, keyed by day of month.

```
content_calendars
  id         string (uuid)
  client     string(100)
  year       int
  month      int            -- 0 to 11, same as JavaScript's Date#getMonth()
  days       json           -- { "8": { "posts": [ {id, type, note} ], "marker": { "label": "Onam" } | null } }
  createdAt, updatedAt
  UNIQUE (lower(client), year, month)

content_calendar_editors
  userId     string (FK users.id, unique)
  createdAt
```

A post is `{ id: string, type: string (max 60), note: string (max 1000, may be "") }`. The `id` is generated by the browser; store it as given.

## Endpoints

| Method and path | Who | Body | Returns |
|---|---|---|---|
| `GET /content-calendar/me` | any user | | `{ "canEdit": boolean, "canManage": boolean }` (`canManage` is true for `super_admin`; `canEdit` is true for `super_admin` and for ticked users) |
| `GET /content-calendar/calendars` | any user | | `CcCalendar[]`, newest first is fine |
| `POST /content-calendar/calendars` | editor | `{ client, year, month }` | the new `CcCalendar` with `days: {}`. `409` with a readable `message` if that client already has that month. |
| `PATCH /content-calendar/calendars/:id` | editor | `{ client?, year?, month? }` | the updated `CcCalendar`. Same `409` rule. |
| `DELETE /content-calendar/calendars/:id` | editor | | `204` |
| `PUT /content-calendar/calendars/:id/days/:day` | editor | `{ posts: Post[], marker: { label } \| null }` | `204` or the day. **Replaces that one day only.** If `posts` is empty and `marker` is null, remove the day's key from `days`. `:day` must be 1 to the number of days in that month. |
| `GET /content-calendar/access` | super_admin | | `[{ id, fullName, email, canEdit }]` for all active employees. Include super admins with `canEdit: true` (they always can). |
| `PUT /content-calendar/access/:userId` | super_admin | `{ canEdit: boolean }` | `204`. Adds or removes the row in `content_calendar_editors`. |

`CcCalendar` is `{ id, client, year, month, days }`.

## Notes

- Errors should use the usual Nest shape `{ "message": "..." }`; the page shows `message` to the user.
- The page re-fetches `GET /calendars` when someone switches back to the tab, so two people editing is fine. Saving a day touches only that day, so edits to different days never overwrite each other.
- Validate lengths (client 100, post type 60, note 1000, marker label 60) and that `posts` and `marker` have the shapes above.
- This should only add new tables (no change to existing ones), like the Projects migration did.
